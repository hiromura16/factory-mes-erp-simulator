# Dokployで汎用SQLデータ投入ツールを設定・検証する

自己管理の隔離された検証環境向けです。Dokployは導入済み、操作は権限を持つ管理者が行う想定です。最初はSQLiteと合成データだけで確認します。実際のアドレス・資格情報・証明書をGitやログへ書かないでください。

## 1. 構成と事前準備

- リポジトリごとに独立したComposeサービスを用意し、本番DBや共有管理画面の状態と分離します。サービスは `app`、コンテナ内ポートは `8080`、ホスト側の例は `127.0.0.1:3560` です。
- `app-data` を `/data` にマウントします。設定DB・暗号鍵・接続用ファイル・履歴・SQLiteのデータが入るので、作業前に復元可能な保護済みバックアップを確認します。UID 1000のアプリユーザーが `/data` に書けることを確認します。
- UI・操作API・メトリクスにアプリ自身のログイン機能はありません。同一オリジン制約は認証ではありません。公開ドメインは追加せず、`BIND_IP=0.0.0.0` にしません。初回はループバックと、必要なら管理者が承認済みの既存の管理アクセス経路だけを使います。

## 2. Gitと環境変数を設定する

1. Dokployで専用プロジェクトを作り、**Docker Compose** を追加します。ソースとしてこのリポジトリ、レビュー済みの対象ブランチ、Composeパス `compose.yaml` を指定します。初回は自動デプロイを使わず、対象コミットを記録します。[Dokploy公式のCompose手順](https://docs.dokploy.com/docs/core/docker-compose)も参照してください。
2. Environment欄のCompose補間用設定に [`.env.example`](../.env.example) を参考に登録します。設定全体をコンテナに渡す `env_file` は追加しません。ポートが予約済みなら `APP_PORT` だけ未使用の値に変えます。
3. SQLiteの初回確認は `SQL_HOST=`、`SQL_PASSWORD_FILE=/dev/null` のままです。既存のボリュームには以前の接続設定が残り得るため、SQLite確認では新規の専用ボリュームを使います。

| 設定 | 初回の例 | 意味 |
| --- | --- | --- |
| `BIND_IP` / `APP_PORT` | `127.0.0.1` / `3560` | ホスト側の待受 |
| `APP_MEMORY` / `APP_CPUS` / `MIN_AVAILABLE_GIB` | `512m` / `1.0` / `6` | 実行上限とホストのメモリ余力下限。余力を確保し、ガードは回避しない |
| `SQL_HOST` / `SQL_PORT` | 空 / `3510` | 既定のSQL Server接続を初回登録する場合のみ、検証用サーバーのホストと実ポートを指定 |
| `SQL_DATABASE` / `SQL_USER` | `FactorySourceLab` / `factory_source_writer` | テストDBと最小権限の専用ユーザーの例 |
| `SQL_PASSWORD_FILE` | `/dev/null` | **ホスト上のファイルパス**。パスワードそのものではない |
| `ORACLE_CLIENT_MODE` | `thin` | Oracleを試す場合のドライバーモード。Thick用クライアントは別途準備 |

SQL Serverで起動時に接続を登録する場合のみ、デプロイ先ホスト上のリポジトリ外にパスワードファイルを用意します。所有権・読取権限を限定し、UID 1000が読める構成にします。Composeはそれをコンテナの `/run/secrets/sql-password` へ読み取り専用でマウントします。作業用チェックアウトには置きません。使用中のDokployが絶対パスのbind mountを制限する場合は、管理者が対象ホスト・Dokployのファイルマウント仕様に合わせ、再取得で消えない保護済みの配置方法を確認してください。ホスト側パスとコンテナ側パスを混同しないでください。既存の接続プロファイルは初回登録用変数の変更では更新されないため、別途設定を確認します。画面で明示的に接続を登録する場合は、このホストファイルが必須ではありません。

## 3. プロキシは必要な層にだけ設定する

| 層 | 確認すること |
| --- | --- |
| Git取得 | Dokployのソース取得側の経路、DNS、Git認証。ビルド引数が効く前の段階 |
| イメージ取得 | `FROM` はdigest固定の `python:3.12-slim`。レジストリには実際のDocker daemon/BuildKitの経路・CA設定が必要。[Docker daemon公式手順](https://docs.docker.com/engine/daemon/proxy/) |
| ビルド中のHTTP(S) | apt、Microsoft ODBCパッケージ取得、pip。DokployのCompose補間環境で次の引数を設定 |
| 実行時 | ビルド引数はコンテナに注入しない。SQLやKerberosの通信はHTTPプロキシで代替せず、経路・DNS・TLS・認証を個別に確認 |

必要な場合は `HTTP_PROXY` と `http_proxy`、`HTTPS_PROXY` と `https_proxy`、`NO_PROXY` と `no_proxy` を、それぞれ同じ値で設定します。大文字・小文字を異なる値にしないでください。`.env.example` の例はコメントなので必要な項目だけ対応する大小文字の両方を有効にし、DokployのEnvironment欄かローカルの非公開 `.env` に登録します。`scripts/init_local.py` が生成した `.env` では、既定でコメントのままです。Composeは値のない引数を補間環境から解決します。この設定を使わない場合や既存のDockerクライアント設定を使う場合は、6項目を**未設定**にします。空欄を明示すると、その項目の既定値を上書きできます。例の `localhost,127.0.0.1,::1` は直接接続先の例で、組織が許可した宛先のみを追加します。

説明用の値の例（この予約ドメインでは接続できません。実際の値は管理者に確認し、公開ファイルへ書かないでください）:

```dotenv
HTTP_PROXY=http://proxy.example.invalid:3128
HTTPS_PROXY=http://proxy.example.invalid:3128
NO_PROXY=localhost,127.0.0.1,::1
http_proxy=http://proxy.example.invalid:3128
https_proxy=http://proxy.example.invalid:3128
no_proxy=localhost,127.0.0.1,::1
```

`FROM` の取得を切り分けるには、許可された検証環境で、配置と同じDocker daemon・プラットフォームを使って取得を試せます。取得先はDockerfileの `FROM` と同一にします。

```sh
docker pull python:3.12-slim@sha256:05a994d2344eb364cc186910f4fc8786a38215f39f00d0acc25bff33a08f4177
```

別ホストや独立したBuildKitビルダーにはこのキャッシュが共有されるとは限りません。同じホストで取得が成功しても、ビルダーがレジストリのメタデータや認証を再確認する場合があります。ビルドで再び失敗したら、ビルダー自身の経路・認証・CAを分けて確認します。

Docker Compose v5.7.1では、未設定時のクライアント既定値の継承と個別上書きを、ダミー設定によるビルド定義の出力で確認しています。ほかのCompose/BuildKit版や実際の組織プロキシでの接続結果を保証するものではありません。

[Dockerの組み込みビルド引数](https://docs.docker.com/build/building/variables/#proxy-arguments)を使い、Dockerfileで `ARG`/`ENV` として宣言せず、ビルド手順内で表示しません。実値は承認済みの設定にだけ保存し、展開値が出る通常の `docker compose config`、シェルトレース、無加工のログ添付を避けます。CAは管理者が承認した手順で配布し、TLS検証は無効化しません。

## 4. 手動配置し、SQLiteで合成データを確認する

1. レビュー済みチェックアウトで `docker compose --env-file .env.example config --quiet` を実行します。実設定も値を表示せずに検証し、ポート、永続ボリューム、秘密ファイルのマウント元を確認します。
2. DokployのComposeで手動Deployを一度実施します。ステータスを確認し、デプロイ先ホストの管理セッションから `curl -fsS --max-time 5 http://127.0.0.1:3560/healthz` が成功することを確かめます。ホスト側ポートを変えた場合は合わせます。これはアプリの応答確認に過ぎず、DBへの書き込みは未確認です。
3. 隔離環境の画面で「接続先」のSQLiteプロファイルを確認し、接続テストします。「データをつくる」で合成項目・主キーを用意し、プレビューで型・内容を確認します。プレビュー自体は接続も書き込みもしません。
4. 表示されたDDLを確認してSQLiteの専用テストテーブルを作ります。少量の `insert`（例: 3件）を1回だけ実施し、履歴の完了・成功件数と対象テーブルを読み取りで照合します。ヘルス・プレビュー・接続・書き込みの結果を分けて記録します。
5. 外部SQLのテストは別途承認された試験環境のみ。保存済みプロファイルの接続テストを先に実行し、専用テーブルと最小権限のwriterで少量の合成データだけを試します。管理者のDDLと試験の書き込みを分離し、本番DBや既存テーブルを使いません。

## 5. 失敗の切り分けと戻し方

- Git・`FROM`・apt/curl/pipは失敗した層を上表で切り分けます。apt/curl/pipは大文字・小文字の設定、プロキシによる拒否、CA、DNSを調べ、値は記録しません。
- 起動・`/healthz` が失敗したらポート競合、UID 1000に対するボリュームやファイル権限、メモリ余力を確認します。その後の接続・書き込みだけが失敗する場合は、専用プロファイル、対象テーブル、ドライバー、経路・DNS/TLS/認証、スキーマ・DML権限を確認します。
- 新規実行を止め、記録済みの前版コミットと同じ環境設定で再配置します。前版が永続データ形式に対応することを確認し、必要な場合のみ保護済みバックアップから復元します。障害対応で `down -v`、共有ボリューム削除、公開ルーティング追加、権限制限の回避は行いません。再配置しても外部DBへの書き込みは元に戻らないため、試験データは別管理です。
